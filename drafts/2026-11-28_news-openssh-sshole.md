이번 주 보안 기술 노트에서 SSH 로그 분석과 로그 파서를 다뤘는데, 마침 OpenSSH의 비밀번호 인증 우회 취약점 소식이 이어졌습니다. 'SSHole'이라는 별명이 붙은 **CVE-2026-123158**입니다. 미국 CISA가 "실제 공격에 악용된 취약점(KEV)" 목록에 올렸다는 보도가 있어 주목받고 있습니다. 무엇이 문제이고 누가 영향을 받는지, 무엇을 하면 되는지를 입문자 눈높이로 정리합니다.

!> 이 글은 11월 하순 시점에 여러 보안 매체·분석 블로그 보도를 바탕으로 정리했습니다. 영향 버전과 패치 버전은 매체마다 일부 차이가 있습니다. 실제 조치 전에는 반드시 아래 '공식 확인처'에서 현행 정보를 확인하세요.

## 1. 한 줄 요약

**musl libc를 쓰고 PAM 없이 동작하는 리눅스 환경(대표적으로 Alpine Linux)**에서 OpenSSH의 비밀번호 인증을 우회할 수 있는 문제가 보고됐습니다. 보도에 따르면 업스트림에서는 OpenSSH 10.6p2로 고쳐졌고, Alpine은 각 버전 브랜치에 수정 패키지를 내놓았습니다.

## 2. 왜 이름이 붙을 만큼 화제가 됐나

- SSH는 서버 관리의 '정문'이라, 인증 우회는 곧 원격에서 서버에 들어올 수 있다는 뜻입니다.
- Alpine은 크기가 작아 **Docker 컨테이너 기본 이미지**로 아주 많이 쓰입니다. 컨테이너 안에 SSH 서버를 넣어 둔 경우가 생각보다 흔합니다.
- 공유기, 임베디드 장비처럼 musl 기반 경량 리눅스를 쓰는 기기에도 영향이 있을 수 있다는 분석이 나왔습니다.
- CISA의 KEV 목록에 올랐다는 것은 "실제 악용 증거가 있다"고 판단했다는 의미라 대응 우선순위가 높습니다.

## 3. 누가 영향을 받나(보도 기준)

| 환경 | 영향 여부(보도 기준) |
|---|---|
| Alpine Linux + OpenSSH, 비밀번호 로그인 허용 | 영향 가능성 높음, 패치 필요 |
| Alpine 기반 Docker 이미지에 sshd 포함 | 이미지 재빌드 필요 |
| musl 기반 임베디드·IoT 장비 | 제조사 공지 확인 필요 |
| Ubuntu, Debian 등 glibc 배포판 | 영향 대상으로 거론되지 않음(Ubuntu는 영향 없다고 안내했다는 보도) |
| 비밀번호 인증을 끄고 키 인증만 사용 | 취약 경로를 타지 않는다는 분석 |

> 핵심 조건은 세 가지입니다. ① musl libc ② PAM 미사용 ③ 비밀번호 인증 허용. 내 서버가 셋 다 해당하는지부터 확인하세요.

## 4. 무엇이 문제였나(쉬운 설명)

리눅스에서 비밀번호 로그인은 보통 PAM이라는 인증 모듈이 처리합니다. PAM이 없는 경량 환경에서는 OpenSSH가 직접 시스템 계정 정보와 비밀번호를 비교하는데, 보도에 따르면 이 경로에서 **잠긴 계정 처리와 관련된 비교 로직**에 문제가 있어 인증을 통과해서는 안 되는 경우에 통과될 수 있었습니다. 일부 분석 글이 "잠긴 계정이 오히려 입구가 됐다"고 표현한 이유입니다.

세부 공격 방법은 이 글에서 다루지 않습니다. 방어하는 쪽에서 알아야 할 것은 "비밀번호 인증 경로의 문제이고, 패치하거나 비밀번호 인증을 끄면 막힌다"는 점입니다.

## 5. 내 서버 확인 방법

```
# 1) 배포판 확인
cat /etc/os-release

# 2) Alpine이라면 openssh 패키지 버전(리비전) 확인
apk info -v openssh openssh-server 2>/dev/null

# 3) 비밀번호 인증이 켜져 있는지 확인
sudo sshd -T | grep -iE "passwordauthentication|usepam"
```

!> 보도에 따르면 Alpine은 수정 사항을 기존 버전에 덧붙이는(backport) 방식이라, `ssh -V`로 보이는 버전 숫자는 그대로일 수 있습니다. **패키지 리비전(-r 숫자)**으로 판단해야 하고, 버전 문자열만 보는 스캐너는 잘못 판단할 수 있습니다.

## 6. 조치 방법

1. **패키지 업데이트**: Alpine은 `apk update && apk upgrade openssh`. 매체들이 정리한 브랜치별 수정 리비전은 아래 표와 같습니다(공식 보안 트래커로 최종 확인).
2. **Docker 이미지 재빌드**: 기존 컨테이너 안에서 업데이트하는 것보다, 최신 베이스 이미지로 다시 빌드하고 배포하는 것이 정석입니다. `docker pull alpine:<버전>` 후 재빌드.
3. **즉시 완화책**: 패치가 늦어진다면 `/etc/ssh/sshd_config`에 `PasswordAuthentication no` 설정 후 sshd 재시작. 키 로그인이 되는지 **먼저** 확인하세요.
4. **컨테이너에 SSH가 정말 필요한지 재검토**: 대부분은 `docker exec`나 오케스트레이터 기능으로 대신할 수 있습니다.
5. **침해 여부 점검**: 지난 글의 방법으로 `Accepted password` 로그를 확인하고, 모르는 로그인 성공이 있으면 침해사고 절차를 따르세요.

| Alpine 브랜치 | 보도된 수정 openssh 리비전 |
|---|---|
| edge | 10.6_p2-r0 |
| 3.24 | 10.3_p1-r2 |
| 3.23 | 10.2_p1-r1 |
| 3.22 | 10.0_p1-r11 |
| 3.21 | 9.9_p2-r1 |

더 오래된 브랜치의 수정 범위(3.16부터인지 3.19부터인지)는 매체마다 다르게 보도되어, Alpine 공식 보안 트래커 확인이 필요합니다.

## 7. 이번 일에서 배울 점

- **비밀번호 인증보다 키 인증**: 이번 취약점도 키 인증만 쓰는 서버는 취약 경로를 타지 않는 것으로 분석됐습니다. 11/25 글의 SSH 하드닝이 실제로 효과가 있는 이유입니다.
- **컨테이너도 패치 대상**: "컨테이너는 금방 지우니까 괜찮다"가 아니라, 베이스 이미지를 주기적으로 갱신하는 체계가 필요합니다.
- **버전 숫자만 믿지 말기**: 배포판의 백포트 정책 때문에 버전 문자열과 실제 패치 여부가 다를 수 있습니다.
- **KEV 목록 활용**: 수많은 CVE 중 무엇부터 막을지 정할 때, 실제 악용이 확인된 KEV 목록은 좋은 우선순위 기준입니다.
